The write endpoints let you add entries to your OneRep log from any HTTP client: a smart scale, a meal-planning script, a shortcut on your phone, or anything else that can make a POST request. Every endpoint requires a key that carries the `write` scope, and every request body must be valid JSON sent with `Content-Type: application/json`.

<Warning>
  **Writes are not idempotent.** There are no idempotency keys. A retried `POST /v1/food` logs the same meal twice. Only retry on `429` and `5xx` responses. Never retry on `4xx`.
</Warning>

<Warning>
  **Unknown fields return 400.** The API refuses any field it does not recognise rather than silently ignoring it. A typo like `"protien"` returns an `unknown_field` error instead of logging zero grams. Check your spelling against the parameter tables below.
</Warning>

<Note>
  **Deleting needs a separate scope.** The `DELETE` routes require a **Full access** key, and they remove one row at a time by id. There are no bulk-clear operations. Every delete is undoable from the app. `DELETE /v1/custom-metrics/{metricId}` is the widest of them: it takes the metric's whole history and any dashboard widget built on it. To stop a metric syncing without losing what it has collected, unbind it with `POST /v1/custom-metrics/{metricId}` and `healthMetricKey: null` instead.
</Note>

<Note>
  **No AI-billed operations are available via the API.** Coach responses and photo logging are not reachable here.
</Note>

## POST /v1/water: Log a water intake entry

Adds a water intake entry to your log. You can optionally supply a date to back-fill a previous day; without one, the entry is assigned to today in UTC.

**Bounds:** `amountMl` must be between **1 and 5000** millilitres.

### Request body

<ParamField body="amountMl" type="number" required>
  Volume of water to log in millilitres. Must be between 1 and 5000.
</ParamField>

<ParamField body="date" type="string">
  Calendar date to log the entry on, in `YYYY-MM-DD` format. Defaults to today in UTC.
</ParamField>

**Example request**

```bash
curl -s https://<deployment>.convex.site/v1/water \
  -H "Authorization: Bearer onerep_sk_…" \
  -H "Content-Type: application/json" \
  -d '{"amountMl": 500, "date": "2026-04-15"}' | jq
```

**Example response**

```json
{
  "logged": true,
  "date": "2026-04-15",
  "amountMl": 500
}
```

## POST /v1/food: Log a food entry

Adds a food item to your nutrition log. Only `name` and `calories` are required; the macro fields are optional but recommended for accurate daily totals. If you omit `meal`, the entry is filed under `snack`.

### Request body

<ParamField body="name" type="string" required>
  Name of the food or meal item.
</ParamField>

<ParamField body="calories" type="number" required>
  Calorie count for this entry in kcal.
</ParamField>

<ParamField body="protein" type="number">
  Protein content in grams.
</ParamField>

<ParamField body="carbs" type="number">
  Carbohydrate content in grams.
</ParamField>

<ParamField body="fat" type="number">
  Fat content in grams.
</ParamField>

<ParamField body="meal" type="string">
  Meal slot to assign this entry to. One of `breakfast`, `lunch`, `dinner`, or `snack`. Defaults to `snack`.
</ParamField>

<ParamField body="date" type="string">
  Calendar date to log the entry on, in `YYYY-MM-DD` format. Defaults to today in UTC.
</ParamField>

**Example request**

```bash
curl -s https://<deployment>.convex.site/v1/food \
  -H "Authorization: Bearer onerep_sk_…" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "Chicken breast",
    "calories": 330,
    "protein": 62,
    "carbs": 0,
    "fat": 7,
    "meal": "lunch",
    "date": "2026-04-15"
  }' | jq
```

**Example response**

```json
{
  "logged": true,
  "date": "2026-04-15",
  "entry": {
    "name": "Chicken breast",
    "calories": 330,
    "protein": 62,
    "carbs": 0,
    "fat": 7,
    "meal": "lunch"
  }
}
```

## POST /v1/weight: Log a body weight measurement

Records a body weight weigh-in. If a weigh-in already exists for the target date, this **replaces** it rather than creating a second entry, so it is safe to send an updated reading for the same day.

**Bounds:** `weightKg` must be between **20 and 400** kilograms.

### Request body

<ParamField body="weightKg" type="number" required>
  Body weight in kilograms. Must be between 20 and 400.
</ParamField>

<ParamField body="date" type="string">
  Calendar date to record the weigh-in on, in `YYYY-MM-DD` format. Defaults to today in UTC.
</ParamField>

**Example request**

```bash
curl -s https://<deployment>.convex.site/v1/weight \
  -H "Authorization: Bearer onerep_sk_…" \
  -H "Content-Type: application/json" \
  -d '{"weightKg": 84.5, "date": "2026-04-15"}' | jq
```

**Example response**

```json
{
  "logged": true,
  "date": "2026-04-15",
  "weightKg": 84.5
}
```

## POST /v1/body-measurements: Write or correct a check-in

Writes any part of a day's check-in, and corrects one that already exists. This is the endpoint to use when a scale reports more than a weight, or when you need to fix a single field on a day that already has an entry. `POST /v1/weight` remains the shortest path for a plain weigh-in.

**Partial by design:** only the fields you send change. Everything else on that date is left exactly as it was, including measurements, notes, and the progress photo. To blank a value, name it in `clearFields`; omitting a field never deletes it.

### Request body

<ParamField body="date" type="string">
  Calendar date of the check-in, in `YYYY-MM-DD` format. Defaults to today in UTC.
</ParamField>

<ParamField body="weightKg" type="number">
  Body weight in kilograms. Between 20 and 500.
</ParamField>

<ParamField body="bodyFatPct" type="number">
  Body fat percentage. Between 1 and 75.
</ParamField>

<ParamField body="waistCm" type="number">
  Waist circumference in centimetres. Between 1 and 300.
</ParamField>

<ParamField body="hipsCm" type="number">
  Hip circumference in centimetres. Between 1 and 300.
</ParamField>

<ParamField body="chestCm" type="number">
  Chest circumference in centimetres. Between 1 and 300.
</ParamField>

<ParamField body="armsCm" type="number">
  Arm circumference in centimetres. Between 1 and 300.
</ParamField>

<ParamField body="thighsCm" type="number">
  Thigh circumference in centimetres. Between 1 and 300.
</ParamField>

<ParamField body="calvesCm" type="number">
  Calf circumference in centimetres. Between 1 and 300.
</ParamField>

<ParamField body="neckCm" type="number">
  Neck circumference in centimetres. Between 1 and 300.
</ParamField>

<ParamField body="leanBodyMassKg" type="number">
  Lean body mass in kilograms. Between 10 and 300.
</ParamField>

<ParamField body="boneMassKg" type="number">
  Bone mass in kilograms. Between 0.5 and 20.
</ParamField>

<ParamField body="basalMetabolicRateKcal" type="number">
  Basal metabolic rate in kcal per day. Between 500 and 6000.
</ParamField>

<ParamField body="notes" type="string">
  Free-text note attached to the check-in. Up to 2,000 characters.
</ParamField>

<ParamField body="clearFields" type="string[]">
  Names of fields to blank on this check-in, for values you cannot express as a number.
</ParamField>

**Example request**

```bash
curl -s https://<deployment>.convex.site/v1/body-measurements \
  -H "Authorization: Bearer onerep_sk_…" \
  -H "Content-Type: application/json" \
  -d '{
    "date": "2026-04-15",
    "weightKg": 84.2,
    "bodyFatPct": 18.4,
    "leanBodyMassKg": 68.7
  }' | jq
```

<Warning>
  A request with no measurement fields at all is refused rather than treated as an empty write. Send at least one field, or at least one entry in `clearFields`.
</Warning>

<Note>
  Correcting a check-in that came from Apple Health or Health Connect marks it as manual. A later phone sync then leaves that day alone rather than writing over your correction.
</Note>

## POST /v1/workouts: Log a workout session

Records a complete workout session including all exercises and their sets. You may include a total duration and a specific date; without a date the session is assigned to today in UTC.

**Limits:**
- Maximum **20 exercises** per session.
- Maximum **30 sets** per exercise.
- Maximum **2 sessions per calendar day.** A third POST on the same date returns a `400` with an explanation; it is not silently dropped.

### Request body

<ParamField body="exercises" type="object[]" required>
  Array of exercises performed in the session. Each object must include a `name` and a `sets` array.
</ParamField>

<ParamField body="exercises[].name" type="string" required>
  Name of the exercise (for example `"Squat"` or `"Bench Press"`).
</ParamField>

<ParamField body="exercises[].sets" type="object[]" required>
  Array of sets performed for this exercise. Each set must include `reps` and may include `weightKg`.
</ParamField>

<ParamField body="exercises[].sets[].reps" type="number" required>
  Number of repetitions completed in this set.
</ParamField>

<ParamField body="exercises[].sets[].weightKg" type="number">
  Load used for this set in kilograms. Omit for bodyweight exercises.
</ParamField>

<ParamField body="durationMinutes" type="number">
  Total session duration in minutes. Optional.
</ParamField>

<ParamField body="date" type="string">
  Calendar date to assign the session to, in `YYYY-MM-DD` format. Defaults to today in UTC.
</ParamField>

**Example request**

```bash
curl -s https://<deployment>.convex.site/v1/workouts \
  -H "Authorization: Bearer onerep_sk_…" \
  -H "Content-Type: application/json" \
  -d '{
    "durationMinutes": 55,
    "date": "2026-04-15",
    "exercises": [
      {
        "name": "Squat",
        "sets": [
          { "reps": 5, "weightKg": 100 },
          { "reps": 5, "weightKg": 105 },
          { "reps": 5, "weightKg": 105 }
        ]
      },
      {
        "name": "Pull-up",
        "sets": [
          { "reps": 8 },
          { "reps": 7 }
        ]
      }
    ]
  }' | jq
```

**Example response**

```json
{
  "logged": true,
  "date": "2026-04-15",
  "sessionId": "w_abc123",
  "durationMinutes": 55,
  "exerciseCount": 2
}
```

## POST /v1/health/days/{date}: Correct a day's health reading

Pins one field of one day's synced health readings to a figure you supply, and stops the phone overwriting it on the next sync. The date goes in the path; the field and its value go in the body.

### Request body

<ParamField body="field" type="string" required>
  Which reading to correct. One of `sleepMinutes`, `steps`, `restingHeartRateBpm`, `hrvMs`, or `activeEnergyKcal`.
</ParamField>

<ParamField body="value" type="number | null" required>
  The corrected reading, in the metric's stored unit. Pass `null` to release the field, after which the next device sync owns it again.
</ParamField>

**Example request**

```bash
curl -s https://<deployment>.convex.site/v1/health/days/2026-04-15 \
  -H "Authorization: Bearer onerep_sk_…" \
  -H "Content-Type: application/json" \
  -d '{"field": "sleepMinutes", "value": 420}' | jq
```

The response returns the day's full list of pinned fields, which `GET /v1/health/days` also reports per day as `manualFields`.

<Warning>
  Values outside the plausible range for the metric are **rejected with a `400`, not clamped**. A slipped decimal point or a unit mix-up should fail rather than settle into a baseline as a plausible-looking number.
</Warning>

<Note>
  Overrides are per field. Correcting a resting heart rate leaves the same day's step count syncing normally.
</Note>

## POST /v1/custom-metrics: Define a custom metric

Creates a metric the user can track that OneRep has no built-in screen for: migraines, espressos, blood glucose, anything countable.

### Request body

<ParamField body="title" type="string" required>
  Name of the metric. Up to 48 characters.
</ParamField>

<ParamField body="tab" type="string" required>
  One of `body`, `nutrition`, or `training`. For a metric with no `healthMetricKey`, this decides which Health dial it files under: body to Body, nutrition to Nutrition, training to Activity. A bound metric files by the catalogue group of the signal it reads and ignores this.
</ParamField>

<ParamField body="kind" type="string" required>
  How the app draws it. `counter` for whole things tallied through the day, `number` for a figure typed once, `toggle` for did-it-or-not.
</ParamField>

<ParamField body="unit" type="string" required>
  Unit label, up to 16 characters.
</ParamField>

<ParamField body="description" type="string">
  One line about what the metric means. Up to 180 characters.
</ParamField>

<ParamField body="step" type="number">
  How much one tap adds. Between 0.01 and 10,000, defaulting to 1.
</ParamField>

<ParamField body="target" type="number">
  Optional daily target, between 0 and 1,000,000.
</ParamField>

<ParamField body="accent" type="string">
  Colour the app draws it in: `food`, `water`, `workout`, or `progress`. Defaults to `progress`.
</ParamField>

<ParamField body="healthMetricKey" type="string">
  A key from `GET /v1/health/metrics`, to have the health sync fill the metric in instead of the user typing it.
</ParamField>

**Example request**

```bash
curl -s https://<deployment>.convex.site/v1/custom-metrics \
  -H "Authorization: Bearer onerep_sk_…" \
  -H "Content-Type: application/json" \
  -d '{
    "title": "Blood glucose",
    "tab": "body",
    "kind": "number",
    "unit": "mmol/L",
    "step": 0.1,
    "healthMetricKey": "bloodGlucoseMmolL"
  }' | jq
```

<Warning>
  **An unknown `healthMetricKey` is rejected, not stored.** The app's picker cannot produce a bad key; an API client can, and a metric left waiting on a reading nobody will ever send looks broken and is. Fetch `GET /v1/health/metrics` and use a key from it.
</Warning>

## POST /v1/custom-metrics/{metricId}: Update a definition

Changes an existing metric's definition while keeping every value logged against it. Renaming a metric, moving it to another tab, or changing its target does not cost the user their history.

Only the fields you send change. The body takes the same fields as creation, all optional, plus two nullable ones:

<ParamField body="target" type="number | null">
  New daily target, or `null` to drop the target entirely.
</ParamField>

<ParamField body="healthMetricKey" type="string | null">
  A new catalogue key, or `null` to unbind the metric from the health sync. Unbinding leaves the values already stored alone.
</ParamField>

**Example request**

```bash
curl -s https://<deployment>.convex.site/v1/custom-metrics/m_9f2… \
  -H "Authorization: Bearer onerep_sk_…" \
  -H "Content-Type: application/json" \
  -d '{"title": "Morning glucose", "target": null}' | jq
```

## POST /v1/custom-metrics/{metricId}/values: Set a day's value

Writes one metric's value for one date, replacing whatever was there.

### Request body

<ParamField body="value" type="number | null" required>
  The figure to record, or `null` to clear the day.
</ParamField>

<ParamField body="date" type="string">
  Calendar date, in `YYYY-MM-DD` format. Defaults to today in UTC.
</ParamField>

**Example request**

```bash
curl -s https://<deployment>.convex.site/v1/custom-metrics/m_9f2…/values \
  -H "Authorization: Bearer onerep_sk_…" \
  -H "Content-Type: application/json" \
  -d '{"date": "2026-04-15", "value": 5.4}' | jq
```

<Note>
  The day is marked as typed, so a metric bound to the health sync keeps your figure rather than having it overwritten on the next sync. Sending `value: null` clears the day and hands a bound metric back to the health store. Clearing a day that holds nothing is an error, not a silent success.
</Note>

## POST /v1/rest-days: Mark dates as rest days

Marks one or more calendar dates as planned rest days. You can submit up to 31 dates in a single request, which makes it easy to pre-schedule a full month at once.

**Limit:** Maximum **31 dates** per request.

### Request body

<ParamField body="dates" type="string[]" required>
  Array of calendar dates to mark as rest days, each in `YYYY-MM-DD` format. Maximum 31 entries per request.
</ParamField>

**Example request**

```bash
curl -s https://<deployment>.convex.site/v1/rest-days \
  -H "Authorization: Bearer onerep_sk_…" \
  -H "Content-Type: application/json" \
  -d '{
    "dates": [
      "2026-04-16",
      "2026-04-18",
      "2026-04-20"
    ]
  }' | jq
```

**Example response**

```json
{
  "logged": true,
  "count": 3,
  "dates": [
    "2026-04-16",
    "2026-04-18",
    "2026-04-20"
  ]
}
```
